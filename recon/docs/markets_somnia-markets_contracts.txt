<h2 id="the-shared-order-book-core">The shared order-book core</h2>
<p>Binary books take orders through <code>placeBinaryOrder</code> instead (see
<a href="#one-book-two-outcomes-the-order-kind">the order kind</a>). Spot and perp books
expose the same placement entrypoint, covering all order types (GTC /
<code>NormalOrder</code>, <code>FillOrKill</code>, <code>ImmediateOrCancel</code>, <code>PostOnly</code>):</p>
<div class="code-copy"><pre><code class="language-solidity">function placeOrder(
    bool isBid, uint64 userData, uint256 price, uint256 quantity,
    uint64 expireTimestampNs, OrderType orderType,
    SelfMatchingOption selfMatchingOption,
    address builder, uint96 builderFeeBpsTimes1k
) external payable returns (bool success, OrderId id);
</code></pre><button type="button" class="code-copy-btn" data-copy-code aria-live="polite">Copy</button></div>
<ul>
<li><strong><code>expireTimestampNs</code> is mandatory and nanoseconds</strong> — a future unix-ns
timestamp (<code>now_seconds * 1e9 + lifetime_ns</code>); zero or past values are
rejected. There is no &quot;no expiry&quot; sentinel.</li>
<li><strong>A rejected order reverts.</strong> A single-order placement does not return
<code>success == false</code>; it reverts with a typed error. A <code>PostOnly</code> that would
cross reverts <code>PostOnlyWouldCross</code>. A <code>FillOrKill</code> that cannot fill in full
reverts <code>FillOrKillNotFillable</code>. An IOC that fills nothing reverts
<code>ImmediateOrCancelNoFill</code>. A self-match under <code>CancelTaker</code> reverts
<code>SelfMatchCancelTaker</code>. An expiry in the past reverts <code>OrderAlreadyExpired</code>.
Decode the revert data to choose a recovery. The batch calls handle a
rejection differently (see <a href="#batch-writes">Batch writes</a>).</li>
<li><strong>Quantize in integers.</strong> <code>getOrderBookParameters()</code> returns <code>tickSize</code>,
<code>lotSize</code>, and <code>minQuantity</code> in raw token units; off-grid values revert
<code>InvalidPrice</code> / <code>InvalidQuantity</code>.</li>
<li><strong><code>builder</code> / <code>builderFeeBpsTimes1k</code></strong> attribute the order to a
routing/builder frontend and pay it a per-order fee (basis-points × 1000).
Pass <code>(address(0), 0)</code> for none. A non-zero fee requires the order owner to
have opted the builder in first — <code>approveBuilder(builder, maxFeeBpsTimes1k)</code> on the pool (0 revokes) — and is capped by the pool&#39;s
<code>getMaxBuilderFeeBpsTimes1k()</code>; charges emit <code>BuilderFeeCharged</code>. Spot, binary
and perp pools all accept builder values; an unapproved non-zero fee reverts
<code>BuilderNotApproved</code> (spot), <code>BuilderFeeExceedsCap</code> (binary) or
<code>BuilderFeeExceedsApproval</code> (perp).</li>
<li><code>cancelOrder(id)</code> / <code>reduceOrder(id, newQty)</code> manage resting orders; both
revert (rather than no-op) on already-terminal orders — check your local
book or <code>getOrder(id)</code> first. <code>cancelExpiredOrders(ids)</code> and
<code>sweepExpiredAtLevel(isBid, price, maxCount)</code> are permissionless cleanup — the
SDK&#39;s <code>client.listSweepableOrders({ pool?, marketType? })</code> is the work-list for
both, returning <code>orderId</code> / <code>isBid</code> / <code>price</code> per row. Note it is <strong>not</strong>
<code>status: &quot;Expired&quot;</code>: that status means the order was already swept, whereas a
keeper wants orders still <code>Open</code> whose expiry has passed.</li>
<li><code>OrderId</code>s are unique <strong>per pool</strong> — always key by <code>(pool, orderId)</code>.</li>
</ul>

<h3 id="batch-writes">Batch writes</h3>
<p>A quoting loop often changes several orders at once. Spot and perp pools
accept these changes in one transaction. Binary pools reject <code>placeOrders</code>
and <code>amendOrders</code> with <code>UseBinaryPlacement</code>.</p>
<ul>
<li><code>placeOrders(requests)</code> places each request in array order and returns
<code>(successes, ids)</code>, aligned with <code>requests</code>. A request that the book
rejects when it lands (a PostOnly that would cross, a FillOrKill or IOC
that cannot fill, a self-match under <code>CancelTaker</code>, or an expiry in the
past) does not revert the call: its flag is <code>false</code>, its id is <code>0</code>, and the
other requests still apply. Any other failure reverts the whole batch, for
example an off-grid price (<code>InvalidPrice</code>) or a request that the owner
cannot fund.</li>
<li><code>cancelOrders(orderIds)</code> returns one flag per id. It returns <code>false</code> for an
order that is no longer live, where <code>cancelOrder</code> reverts.</li>
<li><code>reduceOrders(requests)</code> applies one <code>(orderId, newQuantityRemaining)</code>
reduction per request.</li>
<li><code>amendOrder(request)</code> re-quotes the resting order <code>oldOrderId</code> with the
terms in <code>newOrder</code>, in one transaction. Use the id that it returns: it can
be different from <code>oldOrderId</code>. A failed amendment reverts with an error
that names the reason, for example <code>PostOnlyWouldCross</code> or
<code>AmendOldOrderGone</code>.</li>
<li><code>amendOrders(requests)</code> amends several orders in one transaction. Deployed
pools do not all report a failed request in the same way. Some pools revert
the whole batch: <code>AmendReplacementRejected(requestIndex, reason)</code> for a
rejected replacement, or <code>AmendOldOrderGone</code> for an old order that is no
longer live. Other pools return id <code>0</code> for that request and apply the other
requests. Handle both results: catch the revert, and check every returned
id. On every pool, a failure that is not a rejection, for example an
off-grid price, reverts the whole batch.</li>
<li>An empty array reverts <code>EmptyBatch</code>.</li>
<li>The batch calls are not <code>payable</code>. A native-token amount that a batch order
needs must already be in your vault balance on that pool (<code>depositNative</code>).</li>
</ul>
<h3 id="operator-keys">Operator keys</h3>
<p>A market maker often holds funds in one key and signs orders with a second
key. Spot and perp pools support this split through an operator registry.
Binary pools do not (see <a href="/markets/somnia-markets/market-making">Market Making</a>).</p>
<ol>
<li>Read the registry address from the pool with
<code>getOperatorPermissionsRegistry()</code>.</li>
<li>From the owner key, give the operator key the function selectors that it
can call. <code>setOperatorApprovalForPool(pool, operator, selectors, true)</code>
covers one pool. <code>setOperatorApprovalGlobal(operator, selectors, true)</code>
covers every official pool. <code>setOperatorDenialForPool</code> removes one pool
from a global grant.</li>
<li>From the operator key, call the <code>…For</code> entry points with the owner&#39;s
address: <code>placeOrderFor(owner, …)</code>, <code>cancelOrderFor(owner, orderId)</code> and
<code>reduceOrderFor(owner, orderId, newQuantityRemaining)</code>. The selector to
grant is the selector of that function: <code>0x80054449</code> for <code>placeOrderFor</code>,
<code>0xe37b444b</code> for <code>cancelOrderFor</code>, <code>0x364c2587</code> for <code>reduceOrderFor</code>.</li>
</ol>
<p>The batch and amend operator entry points use the same grants.
<code>placeOrdersFor</code> needs the <code>placeOrderFor</code> grant, <code>cancelOrdersFor</code> needs the
<code>cancelOrderFor</code> grant, and <code>reduceOrdersFor</code> needs the <code>reduceOrderFor</code>
grant. <code>amendOrderFor</code> and <code>amendOrdersFor</code> need both the <code>placeOrderFor</code>
and the <code>cancelOrderFor</code> grants.</p>
<p>The order belongs to the owner, so its funds and its proceeds are the
owner&#39;s. A call without a grant reverts <code>OnlyApprovedContracts</code>. Read a grant
from the pool with <code>isOperatorAuthorized(owner, operator, selector)</code>.</p>
<p>Two rules need care:</p>
<ul>
<li>A global grant is broad. On the testnets it also covers every perp pool, so
a global <code>placeOrderFor</code> grant lets the operator open leveraged positions
for the owner. Grant per pool to keep an operator on one market.</li>
<li>On a perp pool, an order that the operator sends does not top up margin
from the owner&#39;s wallet. Keep the owner&#39;s MarginBank balance funded (see
<a href="/markets/somnia-markets/typescript/perps">Perps</a>).</li>
</ul>
<h2 id="spot-markets">Spot markets</h2>
<p>Each trading pair is its own <code>SpotPool</code> — live pairs are listed on the
<a href="https://somnia-platform-explorer.vercel.app/markets" target="_blank" rel="noopener noreferrer">markets page</a>. <code>getPoolParams()</code> returns everything static in one call:
<code>(baseToken, quoteToken, makerFeeBpsTimes1k, takerFeeBpsTimes1k, tickSize, minQuantity, lotSize)</code>. A native-token side is reported as a sentinel token
address (not <code>address(0)</code>) — resolve it from <code>getPoolParams</code> rather than
assuming.</p>
<p>Spot semantics are the conventional ones: <code>isBid = true</code> buys base with
quote, a fill is a base ↔ quote swap at the <strong>maker&#39;s</strong> resting price, and
<code>userData</code> is a free 64-bit tag echoed back on the order struct and its
<code>OrderPlaced</code> event. Use it for strategy/generation ids.</p>
<p><strong>Funding.</strong> By default the pool <strong>auto-pulls</strong> the required input from your
wallet at placement (ERC-20 <code>transferFrom</code> after a one-time approval, or
<code>msg.value</code> on native pools) and <strong>auto-delivers</strong> proceeds back on fill,
cancel, or expiry. Size the pull with <code>getAutoPullRequirement(owner, isBid, price, quantity, builderFeeBpsTimes1k)</code>. High-churn integrations should opt
out with <code>setManualVaultMode(true)</code>: <code>deposit</code> once, quote against the vault
balance with no per-order token transfers, <code>withdraw</code> when rebalancing —
for a loop that places and cancels constantly the gas savings compound.</p>
<p><strong>Mark price.</strong> Spot pools push <code>MarkPriceUpdated(asset, markPrice, rawMidpoint)</code> whenever the book midpoint advances — an EMA-smoothed midpoint
plus the raw <code>(bestBid + bestAsk) / 2</code>, an on-chain fair-price feed with no
extra infrastructure.</p>
<h2 id="binary-markets">Binary markets</h2>
<h3 id="discover-markets">Discover markets</h3>
<p><code>BinaryMarketsModule</code> is the market registry (the <code>MarketsCore</code> control plane
holds only operators, venues, and module bindings — no markets). Each market
is a <code>MarketRecord</code> (read via <code>module.markets(marketId)</code>):</p>

<p>Watch the module&#39;s <code>MarketCreated</code> event to discover new markets — <strong>every</strong>
market fires it, whether created directly via <code>createMarket</code> or rolled by a
venue&#39;s <code>MarketCreator</code> (venues run rolling series — hourly up/down and
similar — that create markets continuously), and it is the only creation
event carrying the <code>(operatorId, venueId)</code> origin. <code>marketId</code> is a
module-scoped counter (<code>bytes32(++marketSeq)</code>) that doubles as the CREATE2
salt — unique by construction, not precomputable before the create tx.
<code>module.marketIdByAddress(addr)</code> is the reverse lookup.</p>
<p>Every market carries an immutable kind tag, <code>IMarket.marketType()</code>. This
section describes <strong><code>BINARY_SINGLE_BOOK</code></strong> — the only kind live today. Future
kinds (dual-book, multi-outcome) will carry different tags and different book
semantics: branch on the tag, never on assumptions.</p>
<p>Lifecycle: <code>Listed → Trading → Locked → (Settling) → Resolved | Voided</code>
(<code>BinaryMarket.StatusChanged</code>, plus <code>Resolved</code> / <code>Voided</code>). Orders are only
accepted while the market reports Trading — placement reverts
<code>TradingNotActive</code> otherwise. Cancellation stays open through <code>Locked</code>;
<code>redeem</code> opens at <code>Resolved</code> / <code>Voided</code>.</p>
<h3 id="one-book-two-outcomes-the-order-kind">One book, two outcomes: the order kind</h3>
<p>Each <code>BinaryPool</code> runs a <strong>single</strong> order book. Place an order with
<code>placeBinaryOrder</code> and name its kind:</p>

<td><code>0</code></td>
<td>bid</td>
<td>collateral</td>

<tr>
<td><code>SELL_YES</code></td>
<td><code>1</code></td>
<td>ask</td>
<td>YES tokens</td>

<td><code>2</code></td>

<p>A binary pool rejects <code>placeOrder</code>, <code>placeOrders</code>, <code>amendOrder</code> and
<code>amendOrders</code> with <code>UseBinaryPlacement</code>. <code>userData</code> is
the last argument of <code>placeBinaryOrder</code> and is a free 64-bit tag, as on spot:
the pool stores it and does not read it. <code>placeBinaryOrder</code> takes no native
value; a non-zero <code>msg.value</code> reverts <code>UnexpectedNativeDeposit</code>.</p>
<p>The NO book is price-inverted so the base matcher can cross the two books
without knowing about outcomes: a NO order is submitted at the YES-side
complement, <code>price = oneCollateral − noPrice</code>, where
<code>oneCollateral = 10 ** collateral.decimals()</code>. All prices must satisfy
<code>0 &lt; price &lt; oneCollateral</code>, because a share can never be worth more than one
collateral unit. A price at or above <code>oneCollateral</code> reverts
<code>PriceOutOfBounds</code>, and a zero price reverts <code>InvalidPrice</code>.</p>
<h3 id="escrow-and-funding">Escrow and funding</h3>
<p>Placement escrows worst-case value up front:</p>
<ul>
<li><strong>BUY orders</strong> (<code>BUY_YES</code>, <code>BUY_NO</code>) lock collateral (ceil-rounded
<code>price × quantity</code> in the order&#39;s own frame). The pull is <strong>vault-first</strong>:
free vault balance is consumed before <code>transferFrom</code> on your wallet — so
<code>collateral.approve(pool, …)</code> once per pool. (There is no
auto-pull/manual-vault toggle here; this is the only mode.)</li>
<li><strong>SELL orders</strong> (<code>SELL_YES</code>, <code>SELL_NO</code>) lock the outcome tokens themselves,
pulled from your ERC-6909 balance on the singleton — call
<code>outcomeToken.setOperator(pool, true)</code> once; it covers every market, since
ids are namespaced by pool.</li>
</ul>
<p>Money flows back through two channels worth knowing:</p>
<ul>
<li><strong>Refunds land in your vault balance</strong> — taker surplus (you locked at your
limit price, filled at a better maker price) and cancel/reduce/expiry
refunds credit the pool vault, not your wallet. Because placement is
vault-first, a quoting loop recycles these automatically;
<code>withdraw(collateral, amount)</code> only when rebalancing. Read it with
<code>getWithdrawableBalance(owner, collateral)</code>.</li>
<li><strong>Fill proceeds deliver wallet-first with vault fallback</strong> — if the wallet
transfer fails the pool credits the vault and emits <code>PayoutFallbackToVault</code>.</li>
</ul>
<p>Inventory comes from complete sets:
<code>module.mintCompleteSet(operatorId, venueId, marketId, amount)</code> turns <code>amount</code>
collateral into <code>amount</code> YES + <code>amount</code> NO (<code>setOperator(module, true)</code> once
for the merge/redeem directions; <code>operatorId</code>/<code>venueId</code> are routing
attribution only — pass <code>0</code> / <code>bytes32(0)</code> for none);
<code>mergeCompleteSet(operatorId, venueId, marketId, amount)</code> is the inverse;
<code>redeem(operatorId, venueId, marketId, outcomeIdx, amount)</code> burns the winning
side 1:1 after resolution (or either side at 1/2 on void). You can also call
the pool&#39;s <code>mintSet</code> / <code>burnSet</code> / <code>redeem</code> directly. Note you often need
<strong>no inventory at all</strong> to quote — see the fill paths below.</p>
<p>On a <strong>resolved</strong> market (never a voided one), the pool skims the venue&#39;s
frozen <code>settlementFeeBpsTimes1k</code> ONCE from the whole winning backing when the
first winning redeem lands (emitting <code>SettlementFeeCharged(feeRecipient, winningBacking, fee)</code>); every winner then redeems for <code>1 − fee</code> per token.
Per-fill maker/taker fees (<code>ProtocolFeeCharged</code>) and the per-order builder
fee (<code>BuilderFeeCharged</code>) are the other two fee rails — all rates are frozen
into the pool at creation from the origin venue&#39;s config and readable via
<code>getBinaryPoolParams()</code>.</p>
<h3 id="the-four-fill-paths">The four fill paths</h3>
<p>Two opposite-kind orders crossing settle by one of four paths (dispatched on
the unordered pair of order kinds):</p>
<table>
<thead>
<tr>
<th>Crossing pair</th>
<th>Path</th>
<th>Settlement</th>
</tr>
</thead>
<tbody><tr>
<td><code>BUY_YES × SELL_YES</code></td>
<td>DIRECT_YES</td>
<td>YES ↔ collateral swap</td>
</tr>
<tr>
<td><code>SELL_NO × BUY_NO</code></td>
<td>DIRECT_NO</td>
<td>NO ↔ collateral swap</td>
</tr>
<tr>
<td><code>BUY_YES × BUY_NO</code></td>
<td>MINT_A_PAIR</td>
<td>Both pay collateral; pool mints a fresh pair, one side each (emits <code>SetMinted</code>)</td>
</tr>
<tr>
<td><code>SELL_YES × SELL_NO</code></td>

<p>The fill price on <code>OrderFilled</code> is always the <strong>maker&#39;s</strong> resting price, in
the YES frame; the NO-side display price is <code>oneCollateral − fillPrice</code>.
There is no on-chain &quot;fill kind&quot; field — consumers derive it from the two
orders&#39; kinds — the SDK exports
<a href="https://prd.smk.somnia.host/docs/typescript/api/index/functions/sideOfKind" target="_blank" rel="noopener noreferrer"><code>sideOfKind</code></a> (the YES/NO
side of a resting order, from the pool&#39;s <code>BinaryOrderPlaced(orderId, kind)</code>
event) and <a href="https://prd.smk.somnia.host/docs/typescript/api/index/functions/fillKind" target="_blank" rel="noopener noreferrer"><code>fillKind</code></a> for
exactly this derivation.</p>
<p><code>getOrderInfo(orderId)</code> exposes the binary-side escrow state per order
(<code>lockedCollateral</code> / <code>lockedOutcome</code>, kind).</p>
<h2 id="perps">Perps</h2>
<p><code>PerpPool</code> extends the same <code>OrderBook</code> core, so everything in
<a href="#the-shared-order-book-core">the shared core</a> and
<a href="#materialize-the-order-book-from-events">materialization</a> carries over
unchanged. On top it adds margin accounting, funding, and liquidations —
with <code>FundingUpdated</code> / <code>OpenInterestUpdated</code> events, and a dedicated
<code>MakerOrderCancelledExceedsPosition</code> removal event (a maker order erased
pre-fill because it would breach the owner&#39;s position limit — treat it as a
removal in a book reducer). Perp markets are live on the Shannon and Hideki
testnets (see <a href="/markets/somnia-markets/typescript/perps">Perps</a>).
<a href="#batch-writes">Batch writes</a> and <a href="#operator-keys">operator keys</a> work on perp
pools as on spot pools, with the differences listed in those sections.</p>
<p><strong>Discovery.</strong> <code>PerpPoolFactory.getPerpPools()</code> lists the markets of a
network. <code>getBaseTokenForPool(pool)</code> returns the base token of one, and
<code>getPoolForBaseToken(baseToken)</code> is the reverse lookup. The factory is
<code>0x516d2cb6de41bE98444e887793946E65989Ba07b</code> on Shannon; the Hideki factory
and markets are in <a href="#hideki-testnet">Hideki testnet</a>.
<code>getMarketStatus()</code> returns <code>0</code> (<code>Active</code>), <code>1</code> (<code>ReduceOnly</code>), <code>2</code>
(<code>Settlement</code>) or <code>3</code> (<code>Delisted</code>). Only an <code>Active</code> market accepts an order
that increases a position. <code>isPriceable()</code> is <code>false</code> while the market cannot
read a usable mark price, so check it before quoting. Read the mark price
with <code>getMarkPrice()</code> or the non-reverting <code>tryGetMarkPrice()</code>, and the oracle
index price and its update time with <code>getIndexPrice()</code>.
<code>getMaxRestingOrdersPerAccount()</code> is the most orders that one account can
rest on the market (<code>0</code> means the pool applies its built-in default).</p>
<p><strong>Prices and sizes.</strong> A price is in collateral units (USDso, 18 decimals) per
one whole base token. <code>getOneBase()</code> returns one whole base token in raw
units, so the notional of an order is <code>price × quantity / getOneBase()</code>.</p>
<p><strong>Margin.</strong> A perp pool keeps collateral in its <code>marginBank()</code>. Approve the
MarginBank to spend the collateral token. <code>deposit(amount)</code> and
<code>withdraw(amount)</code> move margin, and <code>getAccountEquity(account)</code> reads an
account&#39;s equity in the bank. An order that its owner places also tops up
the margin it needs from the owner&#39;s wallet through the same allowance, so a
deposit is optional. Without the allowance, and with no margin in the bank,
the placement reverts in the token&#39;s <code>transferFrom</code>. An order that an operator
places does not top up (see <a href="#operator-keys">Operator keys</a>).</p>
<h2 id="materialize-the-order-book-from-events">Materialize the order book from events</h2>
<p>Every book mutation emits an event, so one pinned snapshot plus the log
stream reproduces the full book — for <strong>any</strong> of the three families. This is
exactly how the protocol&#39;s own indexer and the SDK&#39;s live watches work — the
reducer below is the same one they run (see
<a href="/markets/somnia-markets/typescript/architecture">Architecture</a> for the SDK&#39;s
implementation of it).</p>
<h3 id="snapshot-then-stream">Snapshot, then stream</h3>
<ol>
<li>Pin a block <code>N</code> (<code>eth_blockNumber</code>).</li>
<li>Snapshot both sides with <code>getAllOpenOrdersOffChain</code> <strong>at block <code>N</code></strong> (pass
the block tag explicitly so pagination pages are mutually consistent). Drop
orders whose <code>expireTimestampNs</code> has already passed.</li>
<li>Stream the pool&#39;s logs from <code>N + 1</code> (<code>eth_subscribe(&quot;logs&quot;)</code> over WSS, or an
<code>eth_getLogs</code> loop) and apply them strictly in <code>(blockNumber, logIndex)</code>
order.</li>
</ol>
<h3 id="the-event-reducer">The event reducer</h3>
<p>Keep a map <code>orderId → Order</code> plus per-side level aggregates:</p>
<table>
<thead>
<tr>
<th>Event</th>
<th>Action</th>
</tr>
</thead>
<tbody><tr>
<td><code>OrderPlaced(orderId, placedOrder)</code></td>
<td>Cache the struct; do <strong>not</strong> insert. Fires for every accepted order — <code>placedOrder.quantityRemaining</code> is already the <strong>post-match residual</strong> (the matcher runs before the event), so zero remaining means it fully filled on entry.</td>
</tr>
<tr>
<td><code>OrderRested(orderId)</code></td>
<td>Insert the cached order into the book. This is the <strong>only</strong> insert signal.</td>
</tr>
<tr>
<td><code>OrderFilled(takerId, makerId, qty, takerRem, makerRem, fillPrice)</code></td>
<td>Patch the <strong>maker</strong>: remaining = <code>makerRem</code>, remove at zero. Ignore the taker leg — its state arrives on its own <code>OrderPlaced</code>/<code>OrderRested</code> later in the same tx.</td>
</tr>
<tr>
<td><code>OrderReduced(orderId, newQuantity)</code></td>
<td>Set remaining = <code>newQuantity</code> (not a fill).</td>
</tr>
<tr>
<td><code>OrderCancelled(orderId)</code> / <code>OrderExpired(orderId)</code></td>
<td>Remove (idempotently).</td>
</tr>
<tr>
<td><code>OrderCancelledSelfMatch(orderId)</code></td>
<td>Remove — a same-owner resting maker erased by a <code>CancelMaker</code> self-match.</td>
</tr>
<tr>
<td><code>OrderCancelledPreFill(orderId)</code></td>
<td>Remove — a resting maker pulled by a pre-fill guard before it could fill. The matching loop emits it for <strong>every</strong> pre-fill removal, so handling it covers every present and future guard.</td>
</tr>
</tbody></table>
<p>Family extras, none of which mutate book state: spot pools also emit
<code>MarkPriceUpdated</code> (fair-price telemetry); binary pools emit <code>SetMinted</code> /
<code>SetBurned</code> / <code>Redeemed</code> / <code>SettlementFeeCharged</code> (outcome-supply /
settlement telemetry — mint-a-pair and burn-a-pair fills emit the first two
alongside <code>OrderFilled</code>) and <code>BinaryMarket.StatusChanged</code> (leaves Trading →
no new fills, only cancels from here); perp pools add
<code>MakerOrderCancelledExceedsPosition</code>, <code>MakerOrderCancelledNegativeEquity</code> and
<code>MakerOrderCancelledStaleMark</code>, which <strong>do</strong> mutate the book — treat all three
as removals. They are reason tags emitted alongside the base
<code>OrderCancelledPreFill</code>, so a reducer that handles the base event alone already
removes the order.</p>
<p>Ordering inside a placement tx: settlement hooks and one <code>OrderFilled</code> per
matched maker fire <strong>first</strong>, then the taker&#39;s <code>OrderPlaced</code> (already
residual-adjusted), then <code>OrderRested</code> iff the residual rested. A reducer that
only inserts on <code>OrderRested</code> handles this for free.</p>
<h3 id="the-sharp-edges">The sharp edges</h3>
<ul>
<li><strong>Self-match removals have their own event.</strong> With
<code>SelfMatchingOption.CancelMaker</code>, the matcher erases the same-owner resting
maker and emits <code>OrderCancelledSelfMatch(orderId)</code> (on every book — spot,
binary, perp). Handle it as a removal or your reducer carries a phantom
order whenever <em>any</em> trader self-crosses with <code>CancelMaker</code>. With
<code>CancelTaker</code> the incoming order is rejected instead: a single-order
placement reverts <code>SelfMatchCancelTaker</code>, and <code>placeOrders</code> returns <code>false</code>
for that request.</li>
<li><strong>Expiry is lazy.</strong> Matching walks past expired makers without cleanup;
<code>OrderExpired</code> only fires later (owner&#39;s next placement, or the
permissionless sweeps). Prune locally the moment <code>expireTimestampNs</code> passes —
an expired order can never fill — and treat the eventual event as a no-op.</li>
<li><strong>Make removals idempotent.</strong> Between local pruning and the several removal
paths, &quot;remove an already-absent order&quot; must be a no-op.</li>
<li><strong>Stream gaps.</strong> On WSS reconnect, backfill the missed range with
<code>eth_getLogs</code> before resuming, in windows of at most 1,001 blocks (see
<a href="#networks">Networks</a>). Somnia blocks have instant BFT finality, so a
delivered log is final and no reorg handling is needed; the SDK&#39;s own live
tail does none. If you still want a guard, treat a parent-hash discontinuity
as a reason to re-snapshot rather than to unwind.</li>
</ul>
<h2 id="track-your-own-orders-and-fills">Track your own orders and fills</h2>
<p>Both order-id parameters on <code>OrderFilled</code> are indexed topics, so you can filter
your fills by the ids your <code>placeOrder</code> or <code>placeBinaryOrder</code> calls returned (or
<code>getOwnOpenOrders()</code> after a restart). Alert on <code>PayoutFallbackToVault</code> — a
delivery to your wallet failed and the proceeds are parked in your vault
balance. Reconcile funds with <code>getWithdrawableBalance(owner, token)</code> and, on
binary markets, <code>outcomeToken.balanceOf(owner, yesId | noId)</code> for positions.</p>
