<h2 id="branch-on-the-class-not-the-message">Branch on the class, not the message</h2>
<p>Every SDK error has a concrete class. Test with <code>instanceof</code>, most specific first, and keep a final <code>throw</code> for errors the SDK does not own. <code>InvariantError</code> is the class for an SDK defect; report it and rethrow it instead of using it for control flow.</p>
<div class="code-copy"><pre><code class="language-ts">import {
  ContractRevertError,
  FillHistoryRestartRequiredError,
  FillHistoryUnavailableError,
  IndexerError,
  IndexerWaitTimeoutError,
  InvariantError,
  InvalidInputError,
  PerpPositionChangesUnavailableError,
  RpcError,
  SignerRequiredError,
  SomniaMarketsError,
  TransactionOutcomeUnknownError,
} from &quot;@somnia-chain/markets-sdk&quot;;

try {
  await exchange.createOrder(&quot;SOMI/USDso&quot;, &quot;limit&quot;, &quot;buy&quot;, 10, 0.11);
} catch (e) {
  if (e instanceof TransactionOutcomeUnknownError) {
    // the order may be on chain: look up e.hash before placing it again
  } else if (e instanceof ContractRevertError) {
    // the chain rejected it: read e.errorName
  } else if (e instanceof InvalidInputError) {
    // the call is wrong: fix the arguments, do not retry
  } else if (e instanceof SignerRequiredError) {
    // configure a privateKey, account, or walletClient
  } else if (e instanceof FillHistoryRestartRequiredError) {
    // getUserFillsPage: discard accumulated pages and request page one without a cursor
  } else if (e instanceof FillHistoryUnavailableError) {
    // deploy and reindex a producer that initializes the fill dataset generation
  } else if (e instanceof PerpPositionChangesUnavailableError) {
    // listPerpPositionChangesForFills: show each fill&#39;s own side until the indexer is reindexed
  } else if (e instanceof RpcError || e instanceof IndexerError) {
    // the request did not complete: retry with backoff, or degrade
  } else if (e instanceof InvariantError) {
    console.error(e); // report the SDK defect
    throw e;
  } else if (e instanceof SomniaMarketsError) {
    // NotConfiguredError and anything else the SDK raised
  } else {
    throw e; // not ours: a wallet or an application bug
  }
}
</code></pre><button type="button" class="code-copy-btn" data-copy-code aria-live="polite">Copy</button></div>
<p><code>IndexerWaitTimeoutError</code> comes from the indexer wait, not from the write. Wrap
<code>waitForIndexedBlock</code> when you need to branch on that deadline:</p>
<div class="code-copy"><pre><code class="language-ts">const targetBlock = 1_234_567n; // the confirmed transaction&#39;s block
try {
  await exchange.client.waitForIndexedBlock(exchange.client.config.chain.id, targetBlock);
} catch (e) {
  if (e instanceof IndexerWaitTimeoutError) {
    // the indexer answered but is still behind e.targetBlock
  } else if (e instanceof IndexerError) {
    // the metadata read did not complete: retry with backoff, or degrade
  } else {
    throw e;
  }
}
</code></pre><button type="button" class="code-copy-btn" data-copy-code aria-live="polite">Copy</button></div>
<p>Message text is not stable. <code>errorName</code>, <code>operation</code>, <code>what</code>, <code>cursorGeneration</code>, and <code>servingGeneration</code> are.</p>
<h2 id="decide-from-a-revert">Decide from a revert</h2>
<p><code>ContractRevertError.errorName</code> is the contract&#39;s own error name when the revert data matched a known error. Branch on it with a fallback arm; <code>errorName</code> is <code>undefined</code> for a bare <code>require</code> string or unknown data.</p>
<div class="code-copy"><pre><code class="language-ts">import { ContractRevertError } from &quot;@somnia-chain/markets-sdk&quot;;

try {
  await exchange.trader.placeOrder(params);
} catch (e) {
  if (!(e instanceof ContractRevertError)) throw e;
  switch (e.errorName) {
    case &quot;ExpiredOrderMustBeCancelled&quot;: {
      // An expired maker sits in the way. Sweep the expired orders, then retry.
      const expired = await exchange.client.listSweepableOrders({ pool: params.pool });
      await exchange.trader.cancelExpiredOrders({ pool: params.pool, orderIds: expired.map((o) =&gt; o.orderId) });
      break;
    }
    case &quot;InsufficientBalance&quot;:
    case &quot;ERC20InsufficientBalance&quot;:
      // top up, then retry
      break;
    case &quot;PostOnlyWouldCross&quot;:
      // re-quote one tick away
      break;
    case undefined:
      console.error(&quot;unrecognised revert&quot;, e.reason ?? e.data);
      break;
    default:
      throw e;
  }
}
</code></pre><button type="button" class="code-copy-btn" data-copy-code aria-live="polite">Copy</button></div>
<p><code>e.args</code> holds the decoded arguments in order. <code>IncorrectSender(sender, expected)</code>, for example, is what a cancel of an already-cancelled order returns; <code>expected</code> is the zero address because the order no longer exists.</p>
<h2 id="retry-only-what-can-succeed">Retry only what can succeed</h2>
<p>Retry a read that throws <code>RpcError</code> or <code>IndexerError</code> with backoff; the request never reached a conclusion. A write is different; see the next section. An <code>IndexerUnavailableError</code> is the SDK refusing locally. <code>breaker-open</code>, <code>breaker-trial</code>, and <code>queue-full</code> mean nothing was sent. <code>live-reset</code> can stop a retry backoff after an earlier attempt was sent. Branch on <code>reason</code> rather than waiting a fixed period, because <code>retryAfterMs</code> is meaningful only for <code>breaker-open</code>. Sleep <code>retryAfterMs</code> for <code>breaker-open</code>; retry shortly for <code>breaker-trial</code>, where a trial read is already deciding; back off on your own schedule for <code>queue-full</code>, since this client is saturated and retrying at once is just re-shed; and retry <code>live-reset</code> on the same client, which <code>stopLive()</code> leaves usable. Retrying sooner than the reason allows is what turns a slow indexer into an outage. An <code>IndexerWaitTimeoutError</code> means the indexer answered but did not reach <code>targetBlock</code> before the deadline: wait longer, or read the required state from chain. An <code>AccountViewError</code> means the indexer answered an account-view read, but not with one complete account. It never means an empty account. Retry <code>snapshotUnstable</code>: the account kept changing while it was read. Retry <code>invalidResponse</code> and <code>scopeMismatch</code> later; when they persist, the indexer serves broken data. An <code>IncompleteHistoryError</code> means portfolio analytics stopped before reading every indexed fill: raise or omit <code>maxFillPages</code> when <code>reason</code> is <code>pageBudgetExceeded</code>, and investigate the indexer when it is <code>cursorCycle</code>; it never means an empty portfolio. A <code>FillHistoryUnavailableError</code> means the producer has not initialized its fill-dataset generation: deploy and reindex a compatible producer before trying again. A <code>PerpPositionChangesUnavailableError</code> means the indexer predates perp position changes: show each fill&#39;s own side, and pair the fills again once the indexer is reindexed; retrying the same indexer fails the same way. A <code>FillHistoryRestartRequiredError</code> means a fill-page cursor belongs to a replaced serving dataset: discard the pages already read and restart from page one; retrying with the same cursor fails again. On the smart-account indexed reads, an <code>AccountsIndexerUnavailableError</code> means the accounts indexer is rate-limited or overloaded: wait <code>retryAfterMs</code> when it is set, otherwise back off, and retry. An <code>AccountFeedRestartRequiredError</code> means that chain&#39;s accounts index was rebuilt since the cursor was issued: discard the pages and read again without a cursor. Retry a <code>ContractRevertError</code> only after the state that caused it changes; the same call reverts the same way. Never retry <code>InvalidInputError</code>, <code>NotConfiguredError</code>, <code>NotSupportedError</code>, or <code>SignerRequiredError</code>; fix the code or the configuration. A <code>CollateralOnWrongChainError</code> means the collateral is on another configured chain: bridge the shortfall — the error carries a plan when a route exists — and retry once it lands. A <code>BridgeLiquidityError</code> means a native bridge route&#39;s destination router holds less than the amount, so the SDK sent nothing: retry after the router is seeded, bridge at most <code>available</code> with <code>exchange.bridge.transfer</code>, or fund the destination another way. A <code>BridgeDeliveryTimeoutError</code> means the bridge leg was sent, but its message was not delivered within the timeout. Do not bridge again at once, or the funds move twice. Call <code>delivered(messageId)</code> on the destination Mailbox. When it returns <code>false</code>, wait longer: the message can still land. Two bridge <code>RpcError</code> operations also come after the origin leg was sent: <code>bridge message id</code> and <code>watch bridge delivery</code>. The funds may be in flight, so look up the origin transaction before you retry.</p>
<p>For a binary wallet, <code>IncompletePortfolioError</code> means <code>getClaimable</code> observed
more than 200 nonzero positions. The read returns no incomplete claim array.
Use <code>getClaimablePage</code> and follow <code>nextOffset</code>, including when a page has no
claims. Retrying the same unqualified call cannot recover omitted positions.</p>
<h2 id="retry-a-write-only-after-you-know-its-outcome">Retry a write only after you know its outcome</h2>
<p>A write can fail after its signed transaction reached the node. The SDK then throws <code>TransactionOutcomeUnknownError</code>, a subclass of <code>RpcError</code>. The transaction can still mine, so sending the write again can place the order twice. Test for this class before <code>RpcError</code>.</p>
<p>The error carries <code>chainId</code>, <code>operation</code> and <code>hash</code>. Look up <code>hash</code> before you send again:</p>
<ol>
<li>Read the receipt for <code>hash</code>. If it exists, the transaction mined. Do not send it again. Its <code>status</code> tells you whether the write succeeded (<code>&quot;success&quot;</code>) or reverted (<code>&quot;reverted&quot;</code>).</li>
<li>If there is no receipt, or no <code>hash</code> (a session send gives none), read the state the write changes. For an order, read your open orders at chain head with <code>exchange.client.getOwnOpenOrdersOnchain(pool, owner)</code>; see <a href="/markets/somnia-markets/typescript/how-to/detect-fills">Detect when an order fills</a>.</li>
<li>Send again only when that state shows the write did not happen.</li>
</ol>
<div class="code-copy"><pre><code class="language-ts">import { TransactionOutcomeUnknownError } from &quot;@somnia-chain/markets-sdk&quot;;

try {
  await exchange.trader.placeOrder(params);
} catch (e) {
  if (!(e instanceof TransactionOutcomeUnknownError)) throw e;
  const viem = exchange.client.getViemClient();
  const receipt = e.hash ? await viem.getTransactionReceipt({ hash: e.hash }).catch(() =&gt; null) : null;
  if (receipt === null) {
    // Unknown still: read your open orders at chain head before placing again.
  }
}
</code></pre><button type="button" class="code-copy-btn" data-copy-code aria-live="polite">Copy</button></div>
<p>From the local-signer and session-key executors, a plain <code>RpcError</code> from a write means the node refused the transaction or nothing was sent. Fix the cause (for example a stale nonce or an unfunded account), then send again. Other writes do not guarantee this. A wallet client can fail after it broadcast, and admin, lend and bridge writes do not make the distinction yet. After one of those throws <code>RpcError</code>, check the chain before you send again.</p>
<h2 id="degrade-an-indexer-read">Degrade an indexer read</h2>
<p>An indexer failure is never &quot;no rows&quot;. Catch <code>IndexerError</code> deliberately when a page should render with stale or empty data rather than fail.</p>
<div class="code-copy"><pre><code class="language-ts">import { IndexerError } from &quot;@somnia-chain/markets-sdk&quot;;

const trades = await exchange
  .fetchTrades(&quot;SOMI/USDso&quot;, undefined, 50)
  .catch((e) =&gt; (e instanceof IndexerError ? [] : Promise.reject(e)));
</code></pre><button type="button" class="code-copy-btn" data-copy-code aria-live="polite">Copy</button></div>
<p>Do not apply the same pattern to a chain read: a chain read throws only on real failure, and an empty fallback would hide it.</p>
<h2 id="tell-cancellation-apart-from-failure">Tell cancellation apart from failure</h2>
<p>When you pass <code>signal</code> in the configuration and abort it, in-flight indexer reads re-throw your abort reason, not an <code>IndexerError</code>. Check <code>e.name === &quot;AbortError&quot;</code> before the SDK classes.</p>
<h2 id="decode-a-revert-you-sent-yourself">Decode a revert you sent yourself</h2>
<p>If you build a transaction with the exported ABIs and send it through your own client, <code>decodeRevert(caught)</code> turns the failure into a <code>ContractRevertError</code> with the same <code>errorName</code> decoding. It always returns an error and never throws. Call it only on failures you know are reverts; a transport error passed to it comes back without <code>errorName</code>.</p>
<div class="code-copy"><pre><code class="language-ts">import { decodeRevert } from &quot;@somnia-chain/markets-sdk&quot;;

try {
  await wallet.writeContract(request);
} catch (caught) {
  const revert = decodeRevert(caught);
  console.error(revert.errorName ?? revert.reason);
}
</code></pre><button type="button" class="code-copy-btn" data-copy-code aria-live="polite">Copy</button></div>
